# Execution Plan R3 — Plano vertical fiéis às fontes

## 0. Escopo e invariantes

- **Produto**: Truco Online PoC v0.1, navegador responsivo apenas.
- **Jogadores**: exatamente 2 humanos, sem autenticação, sem AI, sem WebRTC, sem app mobile.
- **Rede**: Socket.IO com servidor autoritativo; cada cliente recebe *somente* seu estado privado.
- **Regras**: cópia literal de `docs/product/truco-paulista-rules-v0.1.md` (sem interpertações).
- **Stack**: React + R3F + three.js (frontend), Node.js + better-sqlite3 WAL (backend), Docker Compose (`truco-online-hml`, `truco-online-dev`).
- **Revisão**: independente com reviewer `cto`; PR contra `release/v0.1`.

## 4. Critérios de aceite por categoria

### 4.1. Fundação TDD (backend puro)
- Red: todos os testes unitários falham ao rodar `npm test -- tests/e2e/validation.test.js`.
- Green: commit faz passar todas as suite; refatoração apenas depois.
- Artefato: `server/src/validation/hand.js` (implementação mínima que satisfaçao os testes).
- Base de dados: tabela inicial no `better-sqlite3` com uma conta test e estado da mesa (`deal_id`, `turn_index`, `hands[]`).

### 4.2. Lobby/Frontend
- Red: componentes criados como stubs.
- Green: todos os componentes renderizam sem erros, navegação responsiva funciona.
- UI: tela de lobby listando salas disponíveis e botão “Unir”; estado do usuário (nome, token opcional).

### 4.3. Servidor autoritativo
- Red: socket simulado envia estado completo para todos clientes (falha).
- Green: cada cliente recebe `{"playerId": "bob", "hand": [...], "turnIndex": 1}`; o servidor decide quem vira/come.
- Privacidade: sem WebRTC, sem `container_name` global; portas e volumes explicitos no Compose.

### 4.4. Cena 3D (R3F)
- Red: canvas plano sem cartas/avatars.
- Green: cartas instanciadas em posições corretas, ângulos de perspectiva adequados para dois jogadores lado a lado.
- Performance: frame rate estável > 50 FPS em máquina PoC; cena limpa ao sair da sala.

### 4.5. Homologação e segurança
- Red: contêiner sem health check.
- Green: `/health` devolve `{"status":"ok"}`; logs do servidor no stdout; nenhuma credencial exposta.

## 6. Dependências e prerrequisitos por card filho

- **TDD**: rodar `npm test` após cada `git commit`.
- **CI green**: pipeline GitHub Actions roda suite completa; antes de solicitar review, confirmar `gh pr checks --silent=false <pr-number>` com status `"success"`.
- **Revisão independente**: reviewer diferente do implementador (ex: `cto` para todos os cards deste plano R3).
- **max_runtime**: 2h para qualquer card que envolva implementação/testes; 60m apenas para documentação/revisão.
